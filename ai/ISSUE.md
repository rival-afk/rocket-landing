# ISSUE — вопросы и наблюдения по работе Rocket Landing (API)

Наблюдалось 2026-11-09 при обучении нейросети через HTTP API (`http://127.0.0.1:8080`, win32, GUI-режим).

## Вопросы

1. **Параллельные соединения медленнее последовательных.** README обещает поддержку параллельных соединений, но 16 одновременных запросов `/state` выполнялись ~0.6 c (хуже, чем 16 последовательных ~0.27 c). Похоже, запросы обрабатываются строго по одному (возможно, по одному на кадр). Как задумано на самом деле?

2. **Низкий FPS при большом числе swarm-игр.** При 16 параллельных играх оценка ~25 FPS (вывод: 16 параллельных запросов ≈ 16 кадров). Рендер всех SubViewport одновременно сильно нагружает CPU/GPU. Есть ли способ отключить/упростить рендер неактивных ячеек или снизить нагрузку, сохранив GUI-режим?

3. **Нельзя удалить отдельную swarm-игру.** `/reset` без `lane` перезагружает всю сцену (теряются все созданные lane и счётчики), с `lane` — пересоздаёт одну. Эндпоинта «закрыть lane N» нет. Можно ли добавить `DELETE /lane` или аналог?

4. **Lane 0 в режиме swarm.** README: в параллельных играх при смерти игра замораживается, в solo — перезагрузка сцены. Неясно, как ведёт себя lane 0 (главная игра), если заспавнены дополнительные lane: замораживается или перезагружает сцену (и роняет остальные)?

5. **Стоимость запроса `/control`.** Каждый `/control` возвращает состояние, т.е. он одновременно команда и опрос. Удобно, но неявно. `/control` с несуществующей `lane` возвращает 404 — ок, но хотелось бы явной документации, что ответ `/control` = состояние *после* применения ввода.

6. **Поведение API при перезагрузке сцены.** При `/reset` без `lane` TCPServer перезапускается? Запросы, отправленные в момент перезагрузки, теряются/зависают? Нужны ли ретраи на клиенте и сколько ждать после `/reset` (замерено: ~2 c достаточно)?

7. **`time_scale` и физика.** При `Engine.time_scale = 8..20` физика делает шаги в 8–20 раз больше за кадр. Не туннелирует ли ракета сквозь стены на высокой скорости (CCD)? Какой максимальный безопасный `time_scale`?

8. **Двойной запуск.** При втором запуске RocketLanding.exe первый инстанс продолжает работать, второй поднимается без API (порт занят) и выглядит как «зависшая» игра. Стоит ли при занятом порте выводить окно/уведомление или выходить, чтобы не плодить «мёртвые» окна?

## Наблюдения (не баги, но влияет на обучение)

- Одиночный запрос `/state` или `/health` занимает ~16–17 ms независимо от нагрузки; последовательный опрос 8 lane ≈ 130 ms (~7–8 Гц на lane).
- Счёт растёт только при движении вниз (`depth_m`), полёт вверх счёт не даёт.
- Рекорд `best` общий на все lane и сохраняется в `user://rocket_landing_best.txt`.
- Все swarm-игры детерминированы: одинаковые агенты в одинаковых условиях летят одинаково, различается только ввод.

## Ответы (2026-11-09, после редиплоя игры 1.0.0)

1. Параллельные vs последовательные — исправлено: состояние кэшируется на физтик, TCP_NODELAY, соединение закрывается после ответа. Повторные запросы в тике почти бесплатны.
2. FPS при 16 играх — исправлено: CRASHED-игры не рендерятся (UPDATE_ONCE), HUD ~10 Гц, пещера перестраивается раз в 256 px, сетка до 4 столбцов.
3. Удаление игры — новый `DELETE /lane?lane=N` / `POST /lane/delete` (последнюю удалить нельзя).
4. Lane 0 в swarm — как все: при ≥2 играх замораживается только умершая; перезагрузка сцены только в solo. Зафиксировано в README.
5. `/control` — ответ = снимок состояния ПОСЛЕ применения ввода; задокументировано.
6. Перезагрузка сцены — API в автолоаде RocketApiHost; во время reload отвечает 503 + Retry-After: 1 (ретрайить через ~500 мс); сцена поднимается за 50–200 мс.
7. time_scale/туннелирование — CCD CAST_SHAPE; vel × time_scale / 60; безопасно ≤ 10 при |vel_y| ≤ 1500; для тренировки 2.0–8.0; потолок 20.
8. Двойной запуск — при занятом порту: сообщение + красная плашка в игре; флаг `--quit-if-port-busy` завершает второй экземпляр сразу.

Добавлено в API: `speed`, `angle`, `angle_vel`, `thrust`, `torque`, `time_alive` — тренажёр обновлён (v2: 13 входов, миграция v1-геномов zero-padding).

## Наблюдения по игре (2026-11-09, после 1.0.0)

1. **`angle_vel` на замороженном (CRASHED) lane показывает не физику, а применённый torque:** после смерти `angle` не меняется, но `angle_vel` ровно равен `torque × 4.00` (отправил -1 → -4.00; отправил +1 → +4.00). Если задумано показывать текущий руль — лучше назвать поле иначе (`applied_torque`); если нет — это баг: мёртвое тело не должно иметь угловой скорости.
2. **Самопроизвольный увод носа вправо:** при `torque = 0` за 2 с падения `angle` ушло с 0.0° до ~12.6° вправо (без ввода). Задумано как турбулентность/дрейф, или физика без вращательного демпфирования/гравитационный момент? Непонятно, стоит ли компенсировать в контроллере.
3. **`time_scale` vs частота принятия решений:** управление по HTTP (≈17 мс/запрос, последовательно) ограничивает ~5 решений в секунду на lane; при `time_scale = 2` это ~190 px падения на решение — ракета физически не успевает реагировать и все агенты падают на одном и том же изгибе ~9.8 m. Для тренировки через API работать имеет смысл при `time_scale = 1` (≈95 px/решение) или если можно поднять FPS. Возможно, стоит документировать рекомендуемый `time_scale` для управляющих агентов, а не только для физики.
